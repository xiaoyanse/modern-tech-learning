这次我们改变学习方式：**不再逐个研究技术的底层实现，而是快速建立一张现代技术地图。**

今天先认识 20 项有代表性的技术，覆盖软件架构、数据处理、AI 推理、自动化和 AI Agent。

我会重点告诉你三件事：

**它是什么 → 什么情况下应该想到它 → 如何让 AI 评估它。**

还有一个重要原则：**认识技术不等于必须使用技术。** 很多时候，最好的架构决策恰恰是不引入复杂框架。

## 二、第一组：软件架构与通信

这组技术解决的是：**软件模块怎么通信、怎么部署、怎么管理。**

**1. gRPC** 成熟

让不同进程、不同服务器甚至不同编程语言的软件，通过标准接口互相调用。

**想到它的时机：** 你的软件需要调用另一台电脑上的服务，或者 Rust 后端要和 Python AI 服务通信。

开源：[gRPC](https://github.com/grpc/grpc)

---

**2. NATS** 成熟

一种轻量级消息系统，让不同软件服务之间传递消息、发布事件。

**想到它的时机：** 多个独立服务需要互相通知，但你不希望它们直接依赖彼此。

开源：[NATS Server](https://github.com/nats-io/nats-server)

---

**3. Docker** 成熟

把软件和运行依赖打包成容器镜像，减少部署环境不一致的问题。

**想到它的时机：** 软件需要部署到多台服务器，或者不同项目之间存在环境依赖冲突。

开源：[Moby 容器引擎项目](https://github.com/moby/moby)

---

**4. Kubernetes** 成熟

管理大量容器服务，包括部署、扩容、服务发现和故障恢复。

**想到它的时机：** 你的系统有多台服务器、很多独立服务，而且需要频繁发布、自动恢复和统一管理。

开源：[Kubernetes](https://github.com/kubernetes/kubernetes)

这一组最重要的区别：gRPC 负责调用，NATS 负责消息传递，Docker 负责打包运行，Kubernetes 负责集群编排。

## 三、第二组：数据与存储

这组技术解决的是：**数据放在哪里、怎么快速查询、如何处理大量数据。**

| 技术 | 职责 | 官方入口 |
| --- | --- | --- |
| 5. PostgreSQL | 关系数据库，用于事务和业务事实 | [文档](https://www.postgresql.org/docs/) · [GitHub 镜像](https://github.com/postgres/postgres) |
| 6. Redis | 内存数据系统，常用于缓存、计数和短期状态 | [文档](https://redis.io/docs/latest/) · [GitHub](https://github.com/redis/redis) |
| 7. ClickHouse | 面向大量事件和历史数据的列式分析数据库 | [文档](https://clickhouse.com/docs) · [GitHub](https://github.com/ClickHouse/ClickHouse) |
| 8. DuckDB | 进程内分析数据库，可直接查询 Parquet 等文件 | [文档](https://duckdb.org/docs/stable/) · [GitHub](https://github.com/duckdb/duckdb) |

举个非常简单的例子：

你开发一套业务平台，日常数据放 PostgreSQL；如果后续有大量历史事件需要复杂统计，再考虑 ClickHouse。

如果只是临时分析一批 Parquet 文件，DuckDB 可能比搭建一整套分析平台更方便。

不要认为 PostgreSQL、Redis、ClickHouse、DuckDB 是四个必须一起部署的组件。

## 四、第三组：AI 推理与分布式计算

这组技术解决的是：**AI 模型如何运行得更快，以及如何让多个模型、多个 GPU 协同工作。**

| 技术 | 是什么 | 什么时候想到它 |
|--------|--------|--------|
| **9. ONNX Runtime** | 跨平台模型推理引擎 | 需要在不同开发语言、硬件环境中运行模型 |
| **10. TensorRT** | NVIDIA 的高性能推理 SDK | 使用 NVIDIA GPU，希望优化推理性能 |
| **11. Triton Inference Server** | 模型推理服务软件 | 需要管理多个模型、推理实例和批处理 |
| **12. Ray** | 分布式计算框架 | 需要多台机器协同执行 AI 或数据计算任务 |

相关开源仓库：

- [ONNX Runtime](https://github.com/microsoft/onnxruntime)
- [TensorRT](https://github.com/NVIDIA/TensorRT)
- [Triton Inference Server](https://github.com/triton-inference-server/server)
- [Ray](https://github.com/ray-project/ray) 

这四项技术尤其值得建立清晰的区分。

假设你只有一个 YOLO 模型，需要在一张 NVIDIA GPU 上运行，那么可能只需要 ONNX Runtime 或 TensorRT。

如果你有几十个模型，需要统一提供推理接口，可以进一步考虑 Triton。

如果你的 AI 任务需要分布到多台机器上执行，Ray 才开始体现它的价值。

**不要因为项目使用了 GPU，就自动认为需要 Ray。**

### Ray、KServe 与推理引擎怎么配合？

| 层次 | 典型职责 | 代表项目 |
| --- | --- | --- |
| 执行推理 | 在指定设备上运行模型或优化模型执行 | ONNX Runtime、TensorRT、vLLM |
| 推理服务 | 对外提供请求接口，管理模型实例和批处理 | Triton、Ray Serve |
| 分布式应用计算 | 在集群中调度 Python 任务、Actor 或 AI 应用 | [Ray 文档](https://docs.ray.io/en/latest/) · [GitHub](https://github.com/ray-project/ray) |
| Kubernetes 模型服务 | 用 Kubernetes 资源描述并管理推理服务 | [KServe 文档](https://kserve.github.io/website/) · [GitHub](https://github.com/kserve/kserve) |

已有 Kubernetes 且希望统一部署模型时，评估 KServe。任务包括多阶段计算、动态调度或多个 Python 工作进程时，评估 Ray。单机单模型可以先测延迟与吞吐，再决定是否增加服务层。

## 五、第四组：大模型应用与知识系统

这一组与传统视觉检测不同，主要围绕大语言模型、知识库和语义检索。

**13. Ollama**

让开发者更方便地在本地电脑上运行和管理大模型。

**想到它的时机：** 想快速体验本地 AI、开发离线聊天助手，或者验证本地模型能力。

[GitHub 项目](https://github.com/ollama/ollama)

---

**14. vLLM**

面向大语言模型和部分多模态模型的高性能推理服务引擎。

**想到它的时机：** 准备自己部署大模型 API，需要支持较多并发用户，并提高 GPU 利用效率。

[GitHub 项目](https://github.com/vllm-project/vllm) 

---

**15. RAG（检索增强生成）**

这不是一个单独的软件，而是一类技术方案：让 AI 在回答前检索外部知识，再结合检索内容生成答案。

**想到它的时机：** 需要 AI 阅读企业文档、产品说明书、内部知识库，回答与这些资料相关的问题。

代表项目：[LlamaIndex](https://github.com/run-llama/llama_index)、[LangChain](https://github.com/langchain-ai/langchain)

---

**16. 向量数据库**

用来存储和检索向量表示，适合语义搜索、相似图片检索、知识库检索等。

**想到它的时机：** 需要根据“意思相近”而不仅是关键词相同来搜索内容。

代表项目：[Qdrant](https://github.com/qdrant/qdrant)、[Milvus](https://github.com/milvus-io/milvus) 

这里要建立一个概念：

**RAG 是解决方案，向量数据库是可能使用的技术组件。**

RAG 不一定需要独立的向量数据库。例如 PostgreSQL 配合 pgvector，也可以满足许多中小规模语义检索需求。

## 六、第五组：AI Agent 与开发自动化

这组技术非常值得关注，因为它直接关系到你未来如何让 AI 帮你完成工作。

| 技术 | 它是什么 | 什么时候想到它 |
|--------|--------|--------|
| **17. MCP** | AI 应用与外部工具、数据源连接的标准协议 | 需要让 AI 访问 GitHub、数据库、文件或其他软件 |
| **18. LangGraph** | 用于构建有状态 Agent 工作流的框架 | AI 任务涉及多个步骤、状态、条件分支或人工审批 |
| **19. n8n** | 可视化工作流自动化平台 | 希望把不同 API、应用和 AI 模型连接起来，自动执行流程 |
| **20. GitHub Actions** | GitHub 提供的自动化工作流能力 | 代码提交后自动测试、构建、发布软件 |

代表项目：

- [MCP 开源生态](https://github.com/modelcontextprotocol)
- [LangGraph](https://github.com/langchain-ai/langgraph)
- [n8n](https://github.com/n8n-io/n8n)
- [GitHub Actions Runner](https://github.com/actions/runner)

其中 MCP、Agent 工作流和 AI 自动化仍处于快速演进阶段。n8n 的源代码公开，但其许可证有使用限制，不能简单等同于标准 OSI 开源许可证。

## 七、最重要的部分：学会向 AI 提示技术选型

以后你不需要背下全部技术参数。

你需要学会这样提问。

### 通用技术选型提示词

```text
我准备开发一个软件，需求如下：【填写需求】。

请先分析这个需求涉及哪些技术领域，寻找目前成熟且持续维护的开源项目，重点比较功能完整性、部署难度、性能、许可证、社区活跃度和长期维护成本。

优先复用成熟方案，避免重复造轮子。

请区分必需技术、可选技术和不建议引入的技术，并给出推荐方案、替代方案和官方 GitHub 仓库地址。

不要直接开始编写代码。
```

## 八、今天这 20 项技术，哪些应该优先认识？

如果按照“提升技术视野和 AI 技术决策能力”的目标，我建议这样分配注意力。

| 优先级 | 技术 | 原因 |
|--------|--------|--------|
| 高 | Docker、PostgreSQL、gRPC | 现代软件开发的常见基础设施 |
| 高 | ONNX Runtime、TensorRT、Triton | 理解 AI 模型如何落地 |
| 高 | MCP、LangGraph、n8n | 理解 AI 如何从聊天走向执行任务 |
| 中 | Ray、Kubernetes | 理解大型系统如何扩展 |
| 中 | Redis、ClickHouse、DuckDB | 理解不同数据问题的解决方式 |
| 按需 | vLLM、Ollama、RAG、向量数据库 | 开发大模型应用时重点研究 |

这不是技术价值排行榜，而是学习顺序建议。
