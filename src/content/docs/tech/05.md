这一期，我们认识 **20 项数据库与数据基础设施领域的代表技术**。

你不需要学习 SQL 优化、数据库内核或分布式存储算法。我们的目标是让你以后开发软件时，能够判断：

- 普通业务数据应该存在哪里？
- 几亿条日志、事件和设备数据应该怎么处理？
- AI 知识库、语义搜索需要什么技术？
- 实时数据处理、全文搜索、海量文件存储分别有哪些成熟方案？
- 什么时候应该提醒 AI 使用专门的数据库，而不是把所有数据塞进 MySQL？

## 一、先建立数据库的全局地图

很多人理解数据库，停留在 MySQL、SQLite、Redis 这几个名字上。

但现代数据系统已经发展出很多不同的技术方向。

## 现代数据技术全景图

以 PostgreSQL 或 SQLite 保存事务数据。按需求增加缓存、分析、搜索和流处理。数据进入多个系统后，要同时考虑数据延迟、同步失败和重放。

最重要的概念是：

**现代软件通常不是只使用一种数据库，而是根据数据特点选择不同的存储和处理方式。**

不过，这不意味着每个项目都应该引入五六种数据库。多数中小型软件，使用 PostgreSQL 或 SQLite 就已经能解决大量问题。

接下来，我们按技术类别认识代表项目。

## 二、20 项值得认识的技术与开源项目

### 第一组：业务数据库：软件的基础数据存储

**1. PostgreSQL** 成熟

功能全面的关系型数据库，适合存储用户、业务记录、设备配置、订单、权限等结构化数据。

**想到它：** 需要一个长期稳定、支持复杂查询和事务的主业务数据库。

[GitHub](https://github.com/postgres/postgres)

---

**2. SQLite** 成熟

嵌入式关系型数据库，不需要单独部署数据库服务器。

**想到它：** 单机软件、桌面客户端、移动应用、离线系统。

[官方源码仓库](https://sqlite.org/src/doc/trunk/README.md)

---

**3. TiDB** 成熟 · 分布式

支持水平扩展的分布式 SQL 数据库，兼容 MySQL 协议生态。

**想到它：** 单机关系型数据库难以满足持续增长的数据量或并发需求，希望扩展到多台服务器。

[GitHub](https://github.com/pingcap/tidb)

---

**4. MongoDB** 成熟 · 许可证需关注

文档型数据库，主要使用类似 JSON 的文档结构存储数据。

**想到它：** 数据结构变化频繁，存在大量嵌套文档，且文档查询是主要访问方式。

[GitHub](https://github.com/mongodb/mongo)

这一组的核心判断：

**单机优先考虑 SQLite；通用服务端业务优先评估 PostgreSQL；只有出现明确的文档型或分布式需求时，再考虑 MongoDB、TiDB 等。**

MongoDB 社区服务器采用 SSPL 等授权条款，源码可见不等于符合所有标准开源许可证定义。

### 第二组：缓存、状态与高频访问

| 技术 | 它是什么 | 什么时候想到它 | 项目地址 |
|--------|--------|--------|--------|
| **5. Redis** | 内存数据系统，常用于缓存、计数、临时状态 | 数据库查询太频繁，需要低延迟缓存 | [GitHub](https://github.com/redis/redis) |
| **6. Valkey** | 从 Redis 生态分叉发展而来的开源内存数据系统 | 希望采用社区治理、宽松许可证的 Redis 类方案 | [GitHub](https://github.com/valkey-io/valkey) |
| **7. Dragonfly** | 高性能内存数据系统，兼容部分 Redis 等协议 | 缓存吞吐量大，希望评估更高效的内存服务 | [GitHub](https://github.com/dragonflydb/dragonfly) |

成熟度：Redis、Valkey 已形成成熟生态；Dragonfly 有实际工程应用，但迁移时应验证命令兼容性和运行行为。Redis 的不同版本存在不同许可证安排，选型时应核查具体版本。

你只需要记住：

**缓存通常是为了加速访问，不是为了替代主数据库。**

如果你的软件没有明显的性能瓶颈，完全没必要因为 Redis 很流行就提前引入它。

### 第三组：海量分析与时序数据

**8. ClickHouse** 成熟

面向海量数据分析的列式数据库，擅长日志、事件、统计和复杂聚合查询。

**想到它：** 每天产生数百万条事件，需要快速统计趋势、生成报表。

[GitHub](https://github.com/ClickHouse/ClickHouse)

---

**9. DuckDB** 成熟 · 持续快速发展

可以嵌入应用运行的分析数据库，适合直接分析 CSV、Parquet 等文件。

**想到它：** 想在本地快速分析大量表格或文件，不想搭建数据库服务器。

[GitHub](https://github.com/duckdb/duckdb) 

---

**10. TimescaleDB** 成熟

基于 PostgreSQL 生态的时序数据扩展，适合随时间持续产生的数据。

**想到它：** 设备温度、传感器数值、性能指标、历史趋势。

[GitHub](https://github.com/timescale/timescaledb)

---

**11. Apache Pinot** 成熟 · 专业化

面向低延迟实时分析的分布式数据库。

**想到它：** 大量用户同时查询实时分析看板，需要低延迟聚合查询。

[GitHub](https://github.com/apache/pinot)

这一组有个值得记住的趋势：

**事务型数据库与分析型数据库正在形成更紧密的协作。**

例如 PostgreSQL 保存业务事实，ClickHouse 处理大规模分析查询。可参考 [ClickHouse 的 PostgreSQL 集成](https://clickhouse.com/docs/integrations/postgresql)。

但对于数据量不大的系统，先使用 PostgreSQL 做统计完全合理。

### 第四组：全文搜索与 AI 语义搜索

| 技术 | 它是什么 | 什么时候想到它 | 项目地址 |
|--------|--------|--------|--------|
| **12. OpenSearch** | 搜索和分析引擎，支持全文、日志和向量检索 | 网站搜索、日志检索、混合搜索 | [GitHub](https://github.com/opensearch-project/OpenSearch) |
| **13. Qdrant** | 专注向量相似度与混合检索的数据库 | AI 知识库、以图搜图、语义检索 | [GitHub](https://github.com/qdrant/qdrant) |
| **14. Milvus** | 面向大规模向量检索的数据库 | 海量图片、文本或多模态向量搜索 | [GitHub](https://github.com/milvus-io/milvus) |
| **15. pgvector** | PostgreSQL 的向量检索扩展 | 已经使用 PostgreSQL，希望增加语义搜索 | [GitHub](https://github.com/pgvector/pgvector) |

这四项技术正在发生明显的能力交叉。

例如，OpenSearch 支持向量和混合检索。采用前要验证中文分词、召回质量和索引资源开销。

Qdrant 也支持稠密向量、稀疏向量和混合搜索；Milvus 则强调大规模分布式向量检索。

**所以，AI 知识库不一定必须部署专门的向量数据库。**

如果已经使用 PostgreSQL，可以先让 AI 评估 pgvector。只有在检索规模、性能或功能需求超出当前方案时，再考虑独立向量数据库。

### 第五组：实时数据流与数据湖

**16. Apache Kafka** 成熟

分布式事件流平台，用于传输、保存和分发持续产生的数据事件。

**想到它：** 多个服务需要可靠地消费大量事件，或需要回放历史事件。

[GitHub](https://github.com/apache/kafka)

---

**17. Apache Flink** 成熟

分布式实时数据处理引擎，可以对持续到来的数据进行计算、聚合和转换。

**想到它：** 需要实时分析海量事件流，而不只是把事件保存下来。

[GitHub](https://github.com/apache/flink)

---

**18. RisingWave** 发展中 · 已有工程应用

使用 SQL 等方式处理实时事件流，并持续维护计算结果。

**想到它：** 想要实时更新统计结果，但不希望开发复杂的流计算程序。

[GitHub](https://github.com/risingwavelabs/risingwave) 

---

**19. Apache Iceberg** 成熟 · 持续发展

面向大型分析数据集的开放表格式，帮助不同计算引擎管理和读取数据湖中的表。

**想到它：** 大量数据保存在对象存储中，希望多个分析引擎共同使用。

[GitHub](https://github.com/apache/iceberg)

---

**20. MinIO** 成熟技术路线 · 项目状态需核查

S3 兼容对象存储生态中的代表项目，适合保存图片、视频、模型文件和大量非结构化数据。

**想到它：** 需要自己管理大量文件，而不是把图片和视频直接塞进关系型数据库。

[GitHub](https://github.com/minio/minio)

对于新项目，MinIO 的社区版本、发布状态及许可证应单独核实，也可以比较 Ceph、SeaweedFS 等替代方案。

## 三、把这 20 项技术放进实际场景

这是本期最值得掌握的部分。

| 你的软件遇到了什么需求？ | 应该提醒 AI 评估什么？ |
|--------|--------|
| 开发普通业务管理系统 | PostgreSQL |
| 开发完全离线的单机软件 | SQLite |
| 数据量巨大，需要分布式 SQL | TiDB |
| 查询太频繁，数据库压力大 | Redis、Valkey |
| 几亿条事件需要快速统计 | ClickHouse |
| 本地分析大量 CSV、Parquet | DuckDB |
| 持续保存设备传感器数据 | TimescaleDB |
| 需要网站全文搜索 | OpenSearch |
| AI 知识库语义检索 | pgvector、Qdrant |
| 海量图片相似度检索 | Milvus、Qdrant |
| 多个系统持续传递大量事件 | Kafka |
| 实时处理持续产生的数据 | Flink、RisingWave |
| 建立企业级数据湖 | Iceberg |
| 保存海量图片、视频、模型 | 对象存储，如 Ceph、S3 兼容服务 |

## 四、一个值得关注的新趋势：数据库正在融合

以前我们经常按严格的类别划分数据库：

- 关系型数据库负责业务。
- 搜索引擎负责搜索。
- 向量数据库负责 AI 检索。
- 分析数据库负责统计。

但现在这些能力正在相互融合。

### 数据库能力融合示意

**应用层：业务软件、搜索、AI Agent、分析看板**

这意味着未来的技术选型不应该只问：

“我要做向量检索，选哪个向量数据库？”

而应该问：

**“我现有的数据库能否已经满足向量检索需求？引入一个新数据库，收益是否值得增加的运维复杂度？”**

这才是更有价值的判断。

## 五、你可以直接使用的数据库选型提示词

### 数据库与数据架构调查

```text
我准备开发一个软件，数据需求如下：【填写需求】。

请先判断涉及事务型数据库、缓存、分析型数据库、时序数据库、全文搜索、向量检索、对象存储还是实时数据流。

优先评估是否可以使用一种成熟数据库满足需求，避免过度拆分。

搜索最新官方文档与 GitHub 项目，比较适用方案，重点关注数据规模、查询性能、并发、可靠性、部署运维成本、许可证和未来扩展性。

区分当前必需技术、未来可能需要的技术和不建议引入的技术。

不要直接开始编写代码。
```
