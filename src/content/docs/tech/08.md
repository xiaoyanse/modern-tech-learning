这一期，我们要认识的是一个非常值得关注的领域：

**当一个软件项目不再由一个人或一个 AI 完成，而是由多名开发者、多个 AI Agent 共同开发时，应该使用哪些技术来组织协作、控制质量、避免冲突？**

这次我们不深入 Git 命令、CI/CD 配置或 Agent 通信协议，而是建立完整的技术地图。

## 一、先认识现代软件协作的六个层次

版本隔离 → 任务分配 → 变更审查 → 自动验证 → 统一项目规范 → 集成与交付。

这里先建立一个核心认知：

**多人协作与多 Agent 协作，在软件工程层面有大量共同点。**

无论代码由人还是 AI 编写，都需要明确任务归属、隔离修改、审查变更、自动测试和合并代码。

AI Agent 的出现并没有让这些传统工程方法过时，反而让它们变得更加重要。

## 二、第一组：代码版本与并行开发（1-4）

这是所有协作方式的基础。

| 技术 | 它是什么 | 什么时候想到它 | 成熟度与地址 |
|--------|--------|--------|--------|
| **1. Git** | 记录代码修改历史的版本控制系统 | 任何需要持续维护的软件项目 | 成熟 · [GitHub](https://github.com/git/git) |
| **2. Git Branch** | 在独立分支上开发功能 | 多人或多个 Agent 同时修改项目 | 成熟 · [官方文档](https://git-scm.com/docs/git-branch) |
| **3. Git Worktree** | 为同一仓库创建多个独立工作目录 | 多个 AI Agent 并行开发，避免共用同一工作目录 | 成熟 · [官方文档](https://git-scm.com/docs/git-worktree) |
| **4. GitHub Desktop** | 可视化 Git 客户端 | 不想频繁使用 Git 命令，需要查看分支和代码变更 | 成熟 · [GitHub](https://github.com/desktop/desktop) |

### 这里最值得认识的是 Git Worktree

假设你同时安排三个 AI Agent：

### 三个 AI 并行开发一个项目

**同一个 Git 仓库**

统一代码历史

**通过审查与测试后合并**

Worktree 可以让多个分支同时拥有独立工作目录，而不需要频繁切换分支。Git 官方明确支持这种模式。

**但 Worktree 只解决工作目录隔离，不自动解决两个 Agent 修改同一个接口时的逻辑冲突。**

## 三、第二组：任务管理与代码审查（5-8）

这一组解决的是：谁负责什么、修改了什么、谁来确认。

| 技术 | 它是什么 | 什么时候想到它 | 成熟度与地址 |
|--------|--------|--------|--------|
| **5. GitHub Issues** | 任务、缺陷、需求跟踪 | 希望把软件开发拆成可分配的任务 | 成熟 · [官网](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues) |
| **6. Pull Request（PR）** | 代码变更审查与合并机制 | 任何重要代码修改都需要审核 | 成熟 · [官方文档](https://docs.github.com/en/pull-requests) |
| **7. GitHub Projects** | 可视化任务规划与进度管理 | 多人或多 Agent 需要共享任务状态 | 成熟 · [官网](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects) |
| **8. Linear** | 产品需求、缺陷与研发项目管理工具 | 希望使用独立于 GitHub 的专业任务管理平台 | 成熟商业产品 · [官网](https://linear.app/) |

这一组里，我最希望你理解 **Issue 和 PR 的区别**。

- Issue 表示需要解决什么问题。
- PR 表示准备如何修改代码来解决问题。

例如，Issue 可以写“修复登录页面在小窗口下的布局错误”。

AI 完成修改后提交 PR，里面包含代码变更、测试结果和相关说明。

然后由审查者决定是否合并。

**Issue 是工作任务，PR 是可审查的工作成果。**

## 四、第三组：自动测试、构建与发布（9-12）

当开发者或 AI 完成代码修改后，不能仅凭一句“我已经修好了”就认为任务完成。

这时就需要自动化工程工具。

| 技术 | 它是什么 | 什么时候想到它 | 成熟度与地址 |
|--------|--------|--------|--------|
| **9. GitHub Actions** | GitHub 的自动化工作流平台 | 提交代码后自动运行测试、构建、发布 | 成熟 · [Runner 源码](https://github.com/actions/runner) |
| **10. GitLab CI/CD** | GitLab 的持续集成和交付能力 | 团队使用 GitLab 或自建研发平台 | 成熟 · [项目仓库](https://gitlab.com/gitlab-org/gitlab) |
| **11. pre-commit** | 在提交代码前运行自动检查的工具 | 希望在代码进入仓库前发现格式和常见质量问题 | 成熟 · [GitHub](https://github.com/pre-commit/pre-commit) |
| **12. Renovate** | 自动检查依赖更新并提出变更 | 项目依赖多，需要持续升级和安全维护 | 成熟 · [GitHub](https://github.com/renovatebot/renovate) |

例如，可以让 GitHub Actions 在每次 PR 创建时自动运行测试，并在版本发布时自动打包软件。

这类工具的重要性在于：**它们把“质量要求”变成可以重复执行的检查，而不只是写在文档里的口头约束。**

## 五、第四组：代码质量与安全（13-15）

这一组解决的是：代码可以运行，但是否足够可靠、安全、容易维护？

| 技术 | 它是什么 | 什么时候提示 AI 考虑 | 成熟度与地址 |
|--------|--------|--------|--------|
| **13. CodeQL** | GitHub 生态中的代码语义与安全分析工具 | 希望持续扫描代码中的潜在安全问题 | 成熟 · [GitHub](https://github.com/github/codeql) |
| **14. Semgrep** | 基于规则的静态代码分析工具 | 需要检查危险代码模式、团队编码规范 | 成熟 · [GitHub](https://github.com/semgrep/semgrep) |
| **15. SonarQube** | 代码质量与安全管理平台 | 多人团队需要集中查看质量问题和技术债务 | 成熟 · [GitHub](https://github.com/SonarSource/sonarqube) |

这里需要建立一个重要区别：

**自动测试检查软件是否按照预期工作；静态分析检查代码中是否存在某些已知风险和不良模式。**

两者互补，但都不能保证软件完全没有错误。

对于多 Agent 开发，尤其建议把这些检查放到 PR 流程中，而不是让每个 Agent 自行决定是否执行。

## 六、第五组：多 Agent 协作与规范共享（16-20）

这一组是本期最值得关注的新方向。

**16. AGENTS.md** 发展中的协作约定

在项目中为 AI 编程工具提供统一指引，例如项目结构、开发规范、测试要求。

**想到它：** 多个 AI 工具需要理解同一个项目，避免每次重复说明规则。

[GitHub](https://github.com/agentsmd/agents.md)

---

**17. Agent Skills** 快速发展

把某类任务的操作方法、约束和资源组织成可复用的技能。

**想到它：** 希望不同 Agent 都按照相同的方法执行测试、代码审查或软件发布。

[GitHub](https://github.com/agentskills/agentskills)

---

**18. OpenHands** 活跃发展

AI 软件开发 Agent 平台，支持执行开发任务、管理 Agent 工作环境，并与自动化工作流结合。

**想到它：** 希望把 Issue、代码修改、测试和 PR 串成相对完整的 Agent 开发流程。

[GitHub](https://github.com/OpenHands/OpenHands) 

---

**19. GitHub Agentic Workflows** 技术预览

让 AI Agent 参与 GitHub 仓库自动化，例如分类 Issue、分析 CI 失败、提出代码修改。

**想到它：** 希望仓库中的重复性维护任务可以由 Agent 持续处理。

[GitHub](https://github.com/github/gh-aw)

---

**20. Microsoft Agensh** 前沿实验性项目

微软公开的去中心化多 Agent 协作研究项目，探索大量 Agent 如何发现任务、共享信息、验证结果并协同推进工作。

**想到它：** 想研究大规模 Agent 并行协作，而不满足于一个主 Agent 顺序分配任务。

[GitHub](https://github.com/microsoft/Agensh)

## 七、2026 年最值得关注的三个变化

这次查看最新官方资料，我认为有三个变化尤其值得建立认知。

### 变化一：Worktree 正在成为多 Agent 并行开发的重要基础

以前开发者经常在同一个工作目录里切换分支。

现在多个 AI Agent 可以分别拥有独立工作目录，各自开发，最后通过 PR 汇总。

但这只提供了代码隔离，不提供任务协调和自动合并保证。

### 变化二：Agent 开始进入标准软件工程流程

GitHub Agentic Workflows 的技术预览，以及 OpenHands 的 Agent 工作流方向，都表明 Agent 正在参与 Issue 分类、CI 失败调查、文档维护和 PR 审查。

这比单纯让 AI 在聊天窗口中写代码更接近真正的自动化软件工程。

### 变化三：多 Agent 不一定需要一个复杂的中央调度平台

一些工具采用主 Agent 与子 Agent 分工；另一些研究探索 Agent 自行认领任务和共享进度。

GitHub 的 Copilot SDK 文档已经描述了自定义子 Agent 的工具权限和独立上下文机制。

但需要注意：**Agent 数量增加，不代表开发效率必然提高。** 任务依赖、冲突、重复工作、模型调用成本都可能抵消并行收益。

## 八、最重要的部分：如何组织多 Agent 开发？

假设你准备让四个 AI Agent 同时参与一个软件项目。

我更建议采用下面这种组织方式：

### 推荐的多 Agent 协作模式

**主 Agent / 技术负责人**

拆分任务 · 定义接口 · 确认验收标准

**独立分支 / Worktree / PR**

每项任务有明确的变更范围

**自动测试 + 代码审查 + 集成**

验证通过后合并，必要时人工审批

这里有一个容易被忽略的原则：

**任务能不能并行，首先取决于任务之间是否存在依赖，而不是你有多少个 Agent。**

例如，前端页面与后端 API 可以并行开发，但需要先确定接口契约。如果三个 Agent 同时修改同一个核心数据结构，反而可能产生大量冲突。

## 九、一个快速判断：什么任务适合并行？

| 任务关系 | 建议 |
| --- | --- |
| 各自修改独立模块 | 分别定义验收标准和工作目录，汇总时执行集成测试。 |
| 共用核心接口 | 先冻结接口契约或由单个负责人先完成接口改动。 |
| 影响范围不清 | 先用只读调查列出修改面，再决定是否并行。 |

## 十、以后怎么提示 AI 组织多人、多 Agent 开发？

### 多 Agent 软件工程协作提示词

```text
请作为软件工程负责人，为当前项目制定多人及多 AI Agent 协作方案。

先分析代码仓库结构、模块边界、任务依赖和共享接口，再将工作拆分成可独立验收的 Issues。

对于适合并行的任务，评估 Git Branch 与 Worktree 隔离，通过独立 PR 交付。

制定 AGENTS.md 项目规范、Agent Skills、自动测试、静态分析和代码审查流程。

明确哪些任务可以并行、哪些必须串行、哪些操作需要人工审批。

优先使用成熟工具，避免不必要的复杂平台。

先给出方案和风险，不要直接修改代码。
```

## 十一、这 20 项技术，最应该优先记住哪六项？

| 技术 | 为什么值得记住 |
|--------|--------|
| **Git Worktree** | 多 Agent 并行开发的工作目录隔离 |
| **GitHub Issues** | 将需求拆成可跟踪、可分配的任务 |
| **Pull Request** | 让每次代码修改都可审查 |
| **GitHub Actions** | 自动执行测试、构建和发布 |
| **AGENTS.md** | 让不同 AI 遵守共同的项目规范 |
| **OpenHands** | 理解 Agent 如何进入完整软件工程流程 |

如果你只掌握一个原则，我希望是：

**不要把多个 AI Agent 当成可以随意同时修改代码的程序员，而要把它们组织成有任务边界、有共享规范、有独立工作区、有质量验收的开发团队。**
