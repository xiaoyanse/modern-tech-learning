后端系列第 05 节。设备巡检系统有三种引入第二种语言的理由：复用已有相机 SDK、优化测出的计算热点、让有不同运行环境的模块各自部署。**先决定边界，再选绑定库或通信协议。**

## 三类边界如何选

| 边界 | 适用条件 | 需要承担的代价 |
| --- | --- | --- |
| 进程内绑定（FFI 或语言扩展） | 频繁调用、需要复用原生库、希望减少序列化开销 | 共同部署和升级。要约定内存所有权、异常如何返回、线程模型与 ABI。原生崩溃可能带走宿主 |
| 同机进程间通信（IPC） | 需要独立重启或隔离故障，但模块必须在同一台设备运行 | 可用本地套接字、管道等。传大量图像时要测复制和缓冲。共享内存可以减少复制，但仍需处理同步、生命周期和回收 |
| 跨主机网络接口 | 设备与中心服务分开部署，或双方需要独立发布、扩容 | HTTP/JSON 或 gRPC 能明确通信契约。需要处理网络延迟、认证、超时、重试和版本兼容 |

进程内接口适合高频、细粒度操作，但也要测数据转换成本。网络接口更适合批量调用和独立部署。每帧往返网络调用之前，先估算带宽和尾延迟。

## 三组可落地的组合

| 组合 | 典型方案 | 为什么这么选 | 哪些信号会改变方案 |
| --- | --- | --- | --- |
| **Java + C++** | Java 负责巡检和权限。C++ 负责相机 SDK。如果有稳定的 C 接口，可用 Java FFM 调用，JNI 也可用于接入原生库 | 保留现有 Java 业务系统，复用厂商 SDK。进程内调用适合确认稳定且通信频繁的库 | 驱动卡死或崩溃会连带业务时，把 SDK 移到现场独立进程，通过本地 IPC 或网络 API 上报结果 |
| **Python + Rust** | Python 保持数据编排，Rust 通过 PyO3 做一段已证实的 CPU 热点 | 保留 Python 生态，只替换耗时模块。批量传入数据，可以减少频繁跨边界调用 | 如果时间主要花在数据库、GPU 推理或数据复制，扩展可能收益不大。还要测线程与解释器交互、安装包和目标平台构建 |
| **Python + C++** | Python 负责模型流程，C++ 用已有的相机 SDK 或图像算法，通过 pybind11 暴露接口 | 适合直接复用现成 C++ 代码。可让原生侧批量处理图像 | 如果设备 SDK 不稳定、依赖与 Python 冲突或需要独立升级，优先考虑隔离进程。约定图像缓冲区归属与释放时机 |

Java FFM 调用原生代码时，通常以兼容的 C 接口为边界。若现有库只暴露 C++ 接口，可在外面加一层 C ABI 封装，或由独立进程承接。ABI 是二进制层面的调用约定，影响参数、返回值和库能否互相调用。

## 案例结论：尽量在现场处理图像

如果中心平台只需要设备编号、时间戳、缺陷分类和图片引用，把原始帧留在现场采集进程，再上传结果。部署一台相机试点机，记录端到端延迟、图像复制次数、CPU 和内存，并模拟断网、相机重连和进程崩溃。进程内方案只有在性能收益能覆盖绑定、分发和故障影响时才值得保留。

跨语言交付时写清输入、错误码、超时、单位、时间戳、数据所有权和版本兼容策略。明确哪个模块能安全重试，以及一次请求如何在两侧日志中被关联。
