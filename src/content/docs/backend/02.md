后端系列第 02 节。上一节的设备巡检系统要接入相机、保存记录并生成周报。语言选择可以从一个具体问题开始：**这次最难交付的是业务流程、接设备、跑模型，还是在限定硬件上达到延迟目标？**

## 先筛硬约束，再比较代价

1. **确认能否运行。** 核对部署系统、CPU 架构、厂商 SDK、数据库驱动和公司要求。例如相机厂商只交付某平台的 C++ SDK，这个事实比语言排行榜更有决定性。
2. **确认谁来维护。** 用现有团队能值班、排查和升级的语言建立基线。把招人、发布和安全更新算进成本。
3. **定位真实瓶颈。** 先量 API 的延迟、数据库等待和计算耗时。数据库查询占主要时间时，改写整个服务通常碰不到瓶颈。
4. **用同一负载验证候选。** 保持数据、硬件和功能一致，记录每秒处理量、P95 延迟、内存峰值和部署步骤。P95 是 95% 的请求能在其以内完成的时长，适合观察用户经常碰到的慢请求。

## 常见需求与候选语言

| 场景 | 先看什么 | 候选及取舍 |
| --- | --- | --- |
| 巡检或订单后台，权限和流程复杂 | 是否有现成框架、身份方案和维护团队 | Java / Spring Boot 或 C# / ASP.NET Core 都可起步。若公司已有其中一套生产标准，优先验证复用 |
| 需要把 Python 模型快速变成内部接口 | 模型库、驱动、推理资源和调用量 | Python / FastAPI 可以直接衔接模型生态。测实际推理时延，并把耗时任务放到独立 Worker |
| 大量网络连接、轻量代理或运维工具 | 连接数、内存预算、交付方式 | Go 和 Rust 都可评估。Go 常用于服务和工具，Rust 适合有明确资源或内存安全要求、并具备相应维护能力的团队 |
| 工业设备接入和原生图像计算 | 相机、驱动、操作系统、编译器和 ABI | 复用已有 C++ SDK，先验证单机采集与恢复。其余业务可沿用现有语言，通过接口接入 |

这些例子不是语言排名。同一个巡检后台，用 Python、Java、Go 或 C# 都能实现。区别在于你能否复用现有能力，以及在目标环境里以多低的成本稳定交付。

## 已有 Python 服务变慢时

假设现场应用每帧要做解码、预处理和推理，测试发现大部分时间耗在图像预处理。先比较减少图像复制、调用已有原生图像库和降低无效计算。仍达不到目标时，再用 Rust 或 C++ 试做那一个热点模块，并比较整条链路的 P95。保留 Python 基线可帮助评估引入第二种语言后得到的净收益。

交付决策可以写成一句有条件的话：「首版沿用 Python。若目标设备的预处理 P95 仍超过预算，再试做 Rust 扩展，并验证安装包能在目标平台重建。」这样团队能知道何时重新考虑，而不是永远争论哪种语言更快。
