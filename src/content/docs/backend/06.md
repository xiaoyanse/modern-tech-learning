后端系列第 06 节。设备上报温度，系统要存记录、检查阈值、通知值班员，并给看板提供查询。**先确定调用方现在要知道什么，以及哪些结果稍后到达也可以。**

## 同一条数据可以走不同通道

| 需求 | 首选候选 | 设计重点 |
| --- | --- | --- |
| 手机提交巡检、主管查询状态 | HTTP/JSON，使用 OpenAPI 描述契约 | 明确请求字段、成功状态和错误。调用方要区分「已保存」与「已受理」 |
| 现场网关与内部分析服务交换结构化数据 | HTTP 或 gRPC / Protocol Buffers | 选两端便于维护的协议。测报文、请求量、尾延迟与兼容性。为调用设置时限 |
| 把一份周报交给一个 Worker | 持久化任务队列 | 明确任务何时确认、失败重试多少次、重复执行怎样处理 |
| 同一条告警让通知、统计和审计各自消费 | 可保留和重放的事件流 | 定义事件 ID、保留期和订阅方恢复方式。各消费者要能去重，不能假定全局有序 |

OpenAPI 是 HTTP API 的描述规范，gRPC 是调用框架，Protocol Buffers 提供数据定义与编码。队列或事件流主要处理异步交接，是否能持久化、重放和保证顺序，要看具体配置和使用方式。

## 哪份数据说了算

巡检模块拥有巡检记录，告警模块拥有告警处理状态，报表保存可重新计算的查询结果。同一数据库里的相关写入可以放进一个事务。模块分开部署后，网络通知和另一边的数据库写入通常不能由一个本地事务包住。

例如设备提交超温记录，服务先在同一事务里写巡检记录和一条待发送事件，再由后台程序发送事件。这样可以在事务提交后继续投递，也称为事务发件箱。发送后还没标记成功就崩溃时，事件可能再次发出。通知端用事件 ID 去重，并把发信结果单独记录。如果通知供应商支持幂等键，把同一事件 ID 传给供应商。外部调用结果无法确认时，先查询或复核，再决定是否重发。

## 可接受的延迟与失败

巡检人看到「已保存」时，应能查回已提交记录。通知和看板可以稍后更新，但要给出可接受的延迟，例如试点约定 30 秒内更新，并暴露最后更新时间。API 超时也不代表服务端一定没写入。客户端重试提交时复用同一个请求标识，由服务器判断是旧操作还是新操作。

验收时模拟重复上报、消息重放、通知服务停机和客户端超时。确认数据库里只有一条有效巡检记录，已提交事件恢复后能被投递，重放不会重复触发同一条通知。
