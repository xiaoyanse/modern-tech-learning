后端系列第 08 节。前七节讨论了语言、模块、跨进程边界、通信、数据和部署。这里把它们用在三个项目里。每个案例先给出能运行的基线，再说明什么证据支持升级。

## 案例一：工业视觉检测

**条件。** 相机厂商提供 C++ SDK，检测模型已有 Python 版本，中心系统只需要检测结果和少量异常图片。生产线不能因中心服务短时不可用而停止采集。

**首选。** 现场 C++ 进程负责采集。先在同机运行 Python 推理进程，测量帧交换成本。现场保留待上报结果，中心用 HTTP API 接收结果并保存到 PostgreSQL。中心网络中断时，现场在容量允许的范围内继续记录，恢复后按结果 ID 重传。原始帧按明确的保留策略在现场处理。

**替代与验证。** 低帧率时可用简单 IPC。复制成本影响延迟目标时，再验证共享内存或进程内绑定。用真实产线帧率测 P95、丢帧率和积压上限，模拟断网、相机重连和推理进程退出。只有隔离代价测得过高且原生模块足够稳定时，才考虑合并进程。

## 案例二：企业订单与报表平台

**条件。** 一个团队维护订单、权限和报表。订单状态需要一致，月底有报表高峰。

**首选。** 用团队已有的 Java 或 C# 平台做模块化单体，订单变更走 PostgreSQL 事务，报表用独立 Worker 执行，允许稍后完成。给模块明确写入边界，限制大查询影响订单写入。

**替代与验证。** 测高峰时订单 P95、报表等待时间和数据库资源使用。若查询优化和资源隔离仍无法满足目标，先比较独立查询副本或分析存储。独立团队或发布节奏真正成为约束时，再评估拆报表服务，明确数据延迟和发布兼容策略。

## 案例三：内部任务与自动化平台

**条件。** 定时同步数据和生成文件，个别任务失败可重试。同一个任务重复发送文件会造成误操作。

**首选。** 用团队熟悉的语言实现任务 API 和 Worker，持久化状态与执行记录。每次执行带唯一任务 ID，并给外部副作用设计去重策略。设置任务时限、最大重试次数、人工复核入口和告警。无法确认外部调用结果时，先查状态或人工复核，再决定是否重试。

**替代与验证。** 单机任务量小时，可先用数据库领取任务。多团队并发接入、Worker 需要分组、积压难管理时，再评估 Celery 与 RabbitMQ 等组合。模拟重启和重复投递，确认不会重复发送已完成的文件，且能找到失败原因和恢复入口。

## 把决策留给团队复核

一份架构决策记录可以只有一页。写清场景、硬约束、候选方案、取舍、数据与故障边界、验证方法，以及再次评估的条件。比如：「现场优先保留 C++ 采集与 Python 推理两个进程。若实测帧复制超过延迟预算，再验证共享内存。连续 30 分钟按目标帧率运行，并验证断网恢复与进程重启。」

这样记录的价值是，后续团队可以根据数据改动决策，同时知道要保护哪些已经验证的行为。
