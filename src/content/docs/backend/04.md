后端系列第 04 节。巡检系统现在已有设备接入、异常流转和报表。团队想把三块「拆开」。架构讨论先说清楚：**要拆的是代码职责、进程故障范围，还是部署与发布节奏？**

## 五个概念的分工

| 概念 | 它描述的边界 | 设备巡检例子与代价 |
| --- | --- | --- |
| 单体 | 主要业务作为一个应用交付和部署 | 设备、巡检和报告共用一套发布。联调和事务简单，业务增长后要防止模块互相调用无序 |
| 模块化单体 | 同一个部署单元内有清楚的模块接口与依赖规则 | 巡检通过设备模块的接口查询归属，报告读取授权数据。可以共用数据库，同时约定各模块的写入职责 |
| SDK | 面向调用方交付接口、类型、示例和工具 | 给第三方提供设备上报 SDK。它可以调用单体或服务，需维护版本兼容和错误行为 |
| 插件 | 宿主按接口发现、加载或调用扩展 | 一套巡检应用支持多种相机适配器。进程内插件部署直接，但原生故障可能影响宿主，升级也要验证兼容 |
| 微服务 | 按业务能力划分，并具备独立部署的服务 | 报表由另一团队独立发布和扩容。要处理网络超时、契约、数据同步、监控与跨服务故障 |

同一个方案可以包含 SDK 和插件。例如业务仍是模块化单体，现场相机驱动通过插件替换，第三方通过 SDK 上报巡检。后台报告 Worker 也可以单独跑，业务应用仍可以继续整体交付。

## 报表真的需要拆成服务吗

假设月底生成报表把 CPU 跑满，但所有模块仍由一个团队每周一起发布。先把生成过程交给单独 Worker，并让它只读取必要数据。实测排队时长和业务 API 延迟。如果独立进程就能隔离资源，拆服务的收益可能有限。

如果后来报表需要另一团队独立发布、单独扩容，还要保留历史聚合数据，可以考虑拆服务。先确定报表所需字段与更新频率，约定由谁提供和维护，再逐步把查询迁移。巡检模块继续负责巡检事实，报表按需要维护自己的查询视图。两边同时直接修改同一份表，会让发布和排障重新绑在一起。

## 决策与验收

- **模块化验收**：测试哪些模块允许依赖，明确设备权限和异常状态由谁判断。
- **插件验收**：替换一款相机适配器，测试宿主能否识别不兼容版本，并检查断线或崩溃的影响。
- **拆服务验收**：验证独立部署确实可行，模拟报表服务不可用时，确认巡检仍可提交且报告任务可恢复。
