后端系列第 01 节。用一个设备巡检系统，把后端的各层职责和技术选择串起来。

现场人员扫码找到设备，填写温度与异常描述，拍照后提交。主管要查历史记录、跟进异常，还要为指定设备生成每周的巡检报告。第一版要解决的问题是：**一条记录怎样可靠地存下来，一份耗时的报告怎样在后台做完。**

## 一条巡检记录怎样穿过后端

```text
手机提交巡检 → HTTP API → 校验权限和业务规则 → 数据库提交 → 返回「已保存」
主管申请周报 → HTTP API → 写入报告任务       → 返回任务编号
后台 Worker → 领取任务 → 读取巡检数据 → 生成文件 → 更新任务状态
```

| 层次 | 在巡检系统里负责什么 | 什么时候考虑相应技术 |
| --- | --- | --- |
| 请求入口 | 接收请求、检查字段格式、返回记录编号或错误。反向代理可以在应用前处理 HTTPS 和转发 | 手机和网页可共用一套 HTTP API。平台已提供 HTTPS 时可直接使用平台能力，自管 HTTPS 或需要路由多个应用时再考虑 Caddy |
| 业务逻辑 | 判断员工能否巡检这台设备、温度是否超限、谁能关闭异常单 | 先在一个应用内划分设备、巡检和报告模块。模块边界可以先建立，仍按一个应用部署 |
| 事务数据 | 保存设备、巡检、异常单和任务。超温巡检和对应异常单在同一事务中写入，避免只保存其中一条 | 有关联查询和事务要求时可先用 PostgreSQL。数据库也是回查记录和任务状态的依据 |
| 后台任务 | Worker 生成周报、压缩照片或执行耗时分析。前端可查询进度 | 耗时明显或重启后需要继续处理时，持久化任务状态，再由 Worker 领取。需要专门的任务分发时，可评估 Celery 与 RabbitMQ |
| 文件存储 | 保存巡检照片和 PDF。数据库保存文件标识、归属设备和访问所需的业务信息 | 单机试点可用有备份的持久目录。多实例共享文件或文件增长明显时，再评估对象存储 |
| 部署与可观测性 | 让应用可启动、升级和恢复，并查出「为什么有 30 份报告卡住了」 | 先有日志、健康检查和恢复测试。Docker Compose 可一起启动应用与数据库。需要跨 API 和 Worker 跟踪同一任务时，再评估 OpenTelemetry |

## 周报分析：40 秒、两次点击、一次重启

设定一条巡检记录可在 300 毫秒内保存，生成周报却要 40 秒。主管连续点了两次「生成报告」，服务中途重启一次。设计要分别处理保存、受理、重复请求和任务恢复。

1. **事务提交后显示「巡检记录已保存」。** 如果超温需要创建异常单，可以把记录和异常单写在同一个数据库事务里。提交成功后再返回成功，刷新页面时能查到记录。
2. **任务写入后显示「报告已受理」。** API 返回任务编号。Worker 在后台处理，页面按编号查询「排队中、生成中、已完成、失败」。
3. **两次点击返回同一个任务。** 客户端对同一次生成操作复用批次标识。服务端用报告类型、设备范围、统计周期和批次识别请求，借助数据库唯一约束处理并发。用户明确要求重新生成时，可创建新批次。
4. **重启后恢复任务，并只发布一个结果。** Worker 从数据库重新领取等待任务。已领取的任务可设置认领有效期，超时后再领取。每次执行先生成候选文件，只有仍持有认领权的执行才能提交最终结果。即使重试，用户也只看到这项任务关联的最终报告。

**数据库保存事实和任务状态，队列负责投递待办，Worker 实际执行工作。** 报告量小时，Worker 可以从数据库领取任务。引入消息代理后，仍要处理重试与重复投递。事务用于保护数据库内的共同写入，文件生成和外部消息则各有自己的失败与重试边界。

## 第一版怎么选，后面怎么加

一套合理的起点是 **一个 FastAPI 应用、一个 PostgreSQL 数据库和有备份的照片目录**。周报明显耗时，再加后台 Worker。换成 Spring Boot 或 ASP.NET Core，这些职责依然成立。

| 出现的问题 | 先验证什么 | 可能增加的能力 |
| --- | --- | --- |
| 主管打开看板很慢 | 是查询缺索引，还是反复读取相同的汇总结果 | 先优化查询。重复读取明显且允许短暂旧数据时，再评估 Redis 缓存 |
| 想搜「轴承异响」，编号和日期筛选已不够 | 用实际描述验证中文分词、相关度和高亮需求 | 先比较数据库全文检索的效果。搜索要求或扩容需求提高时，再评估 OpenSearch |
| 月底集中生成报告，任务大量排队 | 单份报告耗时多少，Worker 是否忙满，失败能否恢复 | 先测任务耗时与积压，可增加 Worker。分发、并发和积压管理复杂后再评估专门的消息代理 |
| 现场已有 C++ 相机 SDK，业务后端用 Python | SDK 必须在现场运行吗，后台需要原始帧还是检测结果 | 可把相机接入做成现场独立进程，仅通过 HTTP 或 gRPC 上报所需结果。业务后端仍可维持单体 |

给第一版定几个可检查的结果：巡检提交后能查到记录，两次重复申请返回同一个报告任务，Worker 重启后能恢复积压，备份可以在演练中恢复。根据这些结果和实测瓶颈决定下一步要加什么。
