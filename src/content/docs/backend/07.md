## 从一次可重现的部署开始

| 关注项 | 巡检系统的起点 | 验收证据 |
| --- | --- | --- |
| 项目组织 | 业务、API、Worker 和迁移各有清晰入口。依赖版本固定 | 在干净环境能构建同一版本，安装和启动步骤有记录 |
| 环境和凭据 | 开发、试点和正式环境有各自配置。密钥通过受控方式注入 | 源码、镜像和日志里没有生产密钥，轮换后可以继续运行 |
| 数据库迁移 | 先添加可兼容字段，再逐步切换读写，最后清理旧结构 | 旧版本在迁移期间还能工作。应用回退后，数据库结构仍兼容 |
| 上线流水线 | 测试、构建、部署、验证分开。记录应用和迁移版本 | 发布后能提交巡检、查询结果并生成一份测试报告 |
| 运行与恢复 | 记录结构化日志，观察 API 延迟、任务积压、磁盘和备份 | 能从任务 ID 追到失败原因，并在隔离环境恢复数据和照片 |

## 运行方式的取舍

| 方式 | 适合什么时候 | 要额外考虑什么 |
| --- | --- | --- |
| 直接运行 | 单机边缘设备、已有系统服务机制，或厂商驱动与宿主绑定很紧 | 启停、依赖安装、升级、日志轮转、服务账户 |
| 容器与 Docker Compose | API、Worker、数据库等依赖需要一致地启动，且可先运行于一台主机 | 持久卷、网络、设备透传、备份和主机故障。Compose 便于单机运行，多机高可用需另行设计 |
| Kubernetes | 已有团队负责集群，应用需要多节点调度、滚动发布或分别扩缩容 | 集群升级、存储、网络策略、监控、容量和故障恢复。先确认这些成本值得承担 |

## 故障时先看什么

如果主管看到报告一直排队，先确认 API 仍能保存任务，再看待处理任务数量、最老任务等待时间、Worker 是否存活以及最近一次失败原因。健康检查可以分别反映进程是否存活和应用是否准备好接流量。日志回答发生了什么，指标指出哪里开始积压，追踪可把请求在多个组件之间串起来。

回退演练要覆盖三件事：恢复上一版应用、确认它仍能读写当前数据库、验证数据库和文件备份可用。生产备份的目标要说得具体，例如最多容忍丢失多久的数据、多久内恢复服务。实测达不到目标时再改备份频率或恢复方案。
