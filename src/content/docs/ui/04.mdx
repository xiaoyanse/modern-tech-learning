前三节课，我们认识了 UI 技术组合、Design System，以及不同界面的技术选型。

最后一课，我们不再增加技术名词，而是解决一个真正影响开发质量的问题：

**如何让 AI 从一开始就按照统一的标准开发软件，而不是写完几十个页面之后，再花大量时间修复界面不一致的问题？**

我建议你把 AI 看成一支软件开发团队，而不是一个接到需求就立即写代码的程序员。

你需要掌握的是：**如何组织它的工作、要求它交付什么，以及怎样判断它是否真正完成任务。**

---

## 一、AI 开发 UI 的六阶段流程

| 阶段 | 可验收产物 |
| --- | --- |
| 需求分析 | 用户角色、核心流程、页面和状态清单 |
| 技术选型 | 分层选型表和依赖引入理由 |
| 设计系统 | 令牌、交互状态与共享组件清单 |
| 关键页设计 | 可操作的代表页面原型 |
| 组件与页面开发 | 实际可运行的页面与共享组件 |
| 视觉验收 | 真实窗口中的截图、问题记录和复验结果 |

这个流程最重要的地方是：

**每个阶段都应该有可检查的交付结果，而不是让 AI 一口气完成全部工作。**

例如，需求分析没有确认，就不应该直接开始批量开发页面。

## 二、第一阶段：先让 AI 理解软件，而不是直接画页面

假设你告诉 AI：

> 帮我开发一个现代化、专业、美观的设备管理系统。

这句话看起来很明确，但实际上缺少大量信息。

AI 并不知道：

- 软件主要面向普通用户还是专业操作员？
- 用户最频繁执行什么操作？
- 页面之间如何导航？
- 哪些信息需要实时显示？
- 哪些操作具有较高风险？
- 软件主要运行在桌面还是移动设备？

如果这些问题没有解决，AI 很容易生成一套看起来不错、但并不符合实际工作流程的通用后台模板。

### 正确做法

先要求 AI 输出三个结果：

1. **页面清单**：软件应该有哪些页面。
2. **用户流程**：用户如何完成核心任务。
3. **页面信息结构**：每个页面有哪些主要区域、操作和状态。

### 提示词 1：UI 需求分析

```text
你现在担任产品经理和 UX 架构师。

请根据软件需求，分析用户角色、核心业务流程、页面清单、导航关系，以及每个页面需要展示的信息、操作和状态。

识别高频操作、高风险操作、实时数据和复杂交互。

对缺失的信息提出关键问题，不要自行假设。

先输出页面结构和用户流程，不要编写 UI 代码。
```

## 三、第二阶段：让 AI 选择技术，而不是堆叠技术

当页面和交互需求明确后，才应该进行 UI 技术选型。

例如：

| 需求 | 技术候选 |
|--------|--------|
| 普通界面 | React + Tailwind CSS |
| 按钮、弹窗、表单 | shadcn/ui |
| 复杂表格 | TanStack Table / AG Grid |
| 实时趋势 | ECharts / uPlot |
| 二维交互编辑 | Konva / Fabric.js |
| 三维场景 | Three.js |
| 桌面安装包 | Tauri / Electron |

关键是要求 AI 说明**为什么需要某项技术**，以及有没有更简单的方案。

### 提示词 2：UI 技术选型

```text
请根据已经确认的页面需求进行 UI 技术选型。

区分界面框架、样式体系、基础组件、专业组件、图形渲染和桌面运行环境。

优先复用项目现有技术栈和成熟组件，避免职责重叠和不必要的依赖。

输出推荐技术、适用页面、引入原因、替代方案及维护风险。

不要直接编写代码。
```

## 四、第三阶段：建立 Design System

这是整个流程中最容易被忽略，但又最重要的一步。

你应该让 AI 在开发大量页面之前，先建立统一的设计规范。

### 设计系统的四个基础层次

基础令牌 → 语义变量 → 共享组件 → 页面模板。组件规范应列出默认、禁用、加载、错误、焦点等状态，并规定键盘操作。

我建议要求 AI 交付一份设计系统文档，并明确哪些组件必须复用。

### 提示词 3：建立设计系统

```text
请为当前软件建立统一的 Design System。

定义 Design Tokens、共享组件、页面布局、交互状态、主题和可访问性规范。

明确组件复用规则，并提供设计规范文档。

不要为每个页面单独创造一套视觉风格。
```

## 五、第四阶段：先设计关键页面，再批量开发

我不建议让 AI 一次性开发几十个页面。

更好的方式是：

**先选择一个具有代表性的页面，把它做到足够好，再把设计规范推广到其他页面。**

例如，一个软件有 20 个页面。

可以先选择：

- 一个主监控页面。
- 一个复杂数据管理页面。
- 一个任务配置页面。

这三个页面基本能够覆盖主要的布局、表格、交互和组件需求。

### 推荐的页面开发顺序

**代表性页面原型**

验证信息层级、视觉风格和核心交互

**提炼共享组件与页面模板**

**扩展到其他页面**

复用规范，而不是重新设计

这种方法能减少后期大规模返工。

## 六、第五阶段：组件开发与页面实现

到了这一步，才真正让 AI 开始开发页面。

但你仍然应该给它明确约束：

- 优先使用现有共享组件。
- 新增组件前先检查是否已有同类实现。
- 不允许随意引入新的 UI 组件库。
- 不允许在页面中大量硬编码颜色、间距和圆角。
- 复杂交互应包含加载、失败、空数据等状态。
- 不允许为了视觉效果破坏原有业务逻辑。

### 提示词 4：页面开发

```text
现在开始实现已经确认的页面。

必须遵守现有 Design System 和技术选型方案。

开发前先检查已有组件、页面模板和交互模式，优先复用。

禁止无理由引入新框架、硬编码视觉变量或改变统一交互规范。

分批实现，每批完成后检查功能、布局、主题和组件复用情况。
```

## 七、第六阶段：视觉验收：AI 开发 UI 最关键的闭环

这里我要强调一个问题：

**代码编译成功，不代表 UI 开发成功。**

一个页面可能没有任何编译错误，但仍然存在：

- 按钮位置不一致。
- 表格列宽混乱。
- 弹窗内容溢出。
- 字体过小。
- 暗色模式下文字看不清。
- 页面缩放后布局错乱。
- 功能按钮没有实际响应。
- 实时刷新导致界面卡顿。

所以，视觉验收不能只依赖代码审查。

必须检查真实渲染结果。

## 八、如何让 AI 自动进行视觉审查？

可以要求 AI 使用真实浏览器或桌面运行环境，打开页面并截图，然后与设计规范进行比较。

建议至少检查：

- 典型窗口尺寸。
- 小窗口和高 DPI 缩放。
- 亮色与暗色主题。
- 有数据与无数据。
- 正常、加载和错误状态。
- 复杂交互完成前后。

### 提示词 5：视觉审查与修复

```text
请对当前软件进行完整的 UI 视觉与交互审查。

不要只阅读源码，必须运行软件并检查实际渲染结果。

依据现有 Design System，逐页面检查视觉、布局、组件复用、交互状态、主题、可访问性和性能。

将问题按严重程度分类，说明位置、现象、原因和修复建议。

修复后重新检查实际页面，不要仅凭代码修改就宣称完成。
```

## 九、一个更高级的建议：让 AI 持续遵守规范

前面五段提示词可以分别用于不同阶段。

但如果你希望 AI 长期参与同一个项目，我建议把设计规范作为项目的长期约束，而不是每次聊天都重新说明。

例如：

| 规范类型 | 建议保存的位置 |
|--------|--------|
| UI 设计规范 | `docs/design-system.md` |
| 组件使用规范 | `docs/component-guidelines.md` |
| 页面布局规范 | `docs/layout-guidelines.md` |
| UI 验收清单 | `docs/ui-review-checklist.md` |
| AI 开发约束 | `AGENTS.md` 或对应工具的项目规则文件 |

这些文件名只是推荐示例，可以根据项目实际情况调整。

这样做的价值在于：

**即使以后换了一个 AI 模型，或者让多个 AI 同时参与开发，它们也可以依据同一套明确的项目规范工作。**

但文档本身并不能保证执行。还需要通过代码审查、组件检查、截图对比和自动化测试等方式持续验证。

## 十、把整套流程合并成一个可复制的总提示词

如果你不想每次分阶段复制五段提示词，可以使用下面这一份。

### AI 专业 UI 开发总指令

```text
你现在担任产品经理、UX 设计师、UI 架构师和前端技术负责人。

请帮助我规划并开发一套专业、统一、可维护的软件界面。

必须按照以下六个阶段工作：

1. 需求分析。
2. 技术选型。
3. 建立 Design System。
4. 设计代表性页面。
5. 组件与页面开发。
6. 真实界面视觉验收。

每个阶段都要输出可检查的交付结果。

发现需求不明确时先提问，不要自行假设。

优先复用成熟技术和已有组件，避免重复开发与过度设计。

未经确认，不要跳过规划阶段直接批量开发页面。
```

## 十一、专题总结：你现在应该掌握什么？

经过这四节课，你不需要成为专业 UI 设计师，也不需要掌握 React 或 CSS 的所有细节。

但你应该能够做到：

- 知道 React、Tailwind、shadcn/ui、Tauri 等技术如何组合。
- 知道 Design System 与组件库的区别。
- 知道不同类型页面应该考虑哪些专业 UI 技术。
- 知道如何要求 AI 先建立规范，再开发页面。
- 知道如何通过实际运行和截图检查 UI 质量。
- 知道如何让多个 AI 按照统一规范协作。

**最重要的变化，是从“让 AI 帮我写几个页面”，升级到“让 AI 按照一套专业的软件产品开发流程工作”。**
