title: "不同类型软件的 UI 技术选型"
description: "对照后台、监控、视频、数据表、二维和三维场景。"
---

今天我们不再单独介绍 React、PixiJS、Three.js 等技术，而是换一种方式：

**从软件需要实现的界面效果出发，判断应该选择什么技术，以及哪些技术适合组合。**

这一课最重要的认知是：

**普通 UI、复杂数据组件、二维绘图、视频渲染、三维场景，本质上是不同类型的界面问题，不应该全部交给同一种技术解决。**

## 一、先建立一张完整的 UI 选型地图

| 界面需求 | 优先考虑的技术 | 主要用途 |
|--------|--------|--------|
| 普通管理后台 | React、Vue、shadcn/ui | 页面、表单、按钮、弹窗 |
| 复杂数据表格 | TanStack Table、AG Grid | 排序、筛选、编辑、虚拟滚动 |
| 实时监控仪表盘 | ECharts、uPlot | 曲线、统计、实时趋势 |
| 视频显示与叠加 | Video、Canvas、WebGL | 视频播放、检测框、关键点 |
| 二维交互画布 | Konva、Fabric.js、PixiJS | 拖拽、缩放、标注、图形编辑 |
| 三维可视化 | Three.js、Babylon.js | 3D 模型、数字孪生、空间场景 |
| 桌面客户端 | Tauri、Electron、Qt | 本地窗口、系统 API、安装部署 |

这里有一个很重要的区别：

**React 负责组织整个界面，并不意味着所有内容都必须由 React 直接绘制。**

例如，一个 React 页面中完全可以同时包含：

- shadcn/ui 的按钮。
- AG Grid 的数据表格。
- ECharts 的实时曲线。
- PixiJS 的二维画布。
- Three.js 的三维场景。

它们可以各自负责最擅长的区域。

---

## 二、六类典型软件界面

## 1. 管理后台：以表单、导航、数据管理为核心

管理后台最常见的内容是导航、数据列表、表单、权限配置、操作按钮和弹窗。

**推荐技术组合：**

React 可搭配 Tailwind CSS 与 shadcn/ui。使用 Vue 的项目可评估 [shadcn-vue](https://www.shadcn-vue.com/)，它是独立的社区移植项目。

复杂表格、图表按需增加，不必一开始就引入。

什么时候提醒 AI？

> 这是一个以表单、配置和数据管理为主的软件，请优先使用成熟的 UI 组件体系，不要自研按钮、弹窗、下拉菜单等基础组件。

**不建议：** 为普通管理后台引入 Three.js、PixiJS 等图形引擎。

---

## 2. 工业监控：以实时状态、报警和信息密度为核心

工业监控界面和普通管理后台有明显差异。

它更关注实时状态、异常提示、信息密度和持续运行的可读性。

**推荐技术组合：**

**React + Tailwind + 统一组件库**

整体页面、导航、配置、报警列表

**ECharts**

设备状态与趋势

**Canvas / PixiJS**

设备图形与动态标记

什么时候提醒 AI？

> 这是一个需要长时间运行的实时监控界面。请优先保证信息层级、报警可辨识度、刷新稳定性和可读性，不要为了视觉效果增加不必要的动画。

这里还要注意：报警不能只靠颜色区分，最好同时使用文字、图标或其他明确状态标识。

---

## 3. 实时视频叠加绘制：以画面同步和绘制性能为核心

这类界面可能需要在视频或连续图像上绘制：

- 目标检测框。
- 人体关键点。
- 检测区域和警戒线。
- 文字标签。
- 目标运动轨迹。

这里最容易犯的错误是：**用普通 DOM 元素绘制所有检测结果。**

如果每帧都产生大量检测框和关键点，频繁更新 DOM 可能增加渲染开销。

更合理的是把视频或图像显示与图形叠加作为独立的渲染区域。

### 实时视频叠加的典型结构

视频或图像底层 + 检测结果叠加层

### 怎么选？

| 场景 | 优先评估 |
|--------|--------|
| 少量检测框、关键点、文字 | Canvas 2D |
| 大量图形、复杂交互、频繁更新 | PixiJS |
| 自定义 GPU 渲染、复杂图像处理 | WebGL / WebGPU |
| 需要编辑检测区域、拖拽多边形 | Konva、Fabric.js |

**注意：PixiJS 并不是只要涉及实时视频就必须引入。** 简单检测框绘制，Canvas 2D 可能已经足够。

另外，叠加层应与对应的视频帧或图像帧保持坐标和时间同步。单纯提高绘制 FPS，不能解决检测结果滞后或坐标映射错误的问题。

---

## 4. 复杂表格：以大量数据和高效操作为核心

普通表格组件适合简单列表。

但如果你需要：

- 数万行数据。
- 多列排序和筛选。
- 单元格编辑。
- 列固定、列分组。
- 大量数据虚拟滚动。
- Excel 风格的交互。

就应该考虑专业数据表格技术。

| 技术 | 主要特点 | 什么时候想到它 |
|--------|--------|--------|
| **TanStack Table** | 无头表格逻辑，外观高度自由 | 希望与自己的设计系统深度结合 |
| **AG Grid** | 功能丰富的完整数据表格 | 企业级复杂表格、编辑、分组 |
| **Handsontable** | 类似电子表格的编辑体验 | 需要 Excel 风格的单元格操作 |

相关项目：

[TanStack Table](https://github.com/TanStack/table) · [AG Grid](https://github.com/ag-grid/ag-grid) · [Handsontable](https://github.com/handsontable/handsontable)

AG Grid 的 Community 与 Enterprise 版本、Handsontable 的商用与非商用场景分别适用不同条款。评估前先核对所需功能和相应版本许可。

---

## 5. 二维画布：以拖拽、编辑和交互为核心

假设你要开发一个区域配置工具。

用户需要：

- 在图片上绘制多边形。
- 拖动顶点。
- 缩放画面。
- 选择、删除和修改形状。
- 保存和恢复图形。

这时单纯使用 Canvas API 可能需要自己开发大量交互逻辑。

更合适的候选技术包括：

| 技术 | 优势 | 适用场景 |
|--------|--------|--------|
| **Konva** | 交互图形、拖拽、变换较方便 | 图片标注、区域编辑、可视化编辑器 |
| **Fabric.js** | 面向可编辑画布对象 | 设计编辑器、图片标注、图形操作 |
| **PixiJS** | 强调高性能二维渲染 | 大量动态元素、复杂实时画布 |

官方项目：

[Konva](https://github.com/konvajs/konva) · [Fabric.js](https://github.com/fabricjs/fabric.js) · [PixiJS](https://github.com/pixijs/pixijs)

**这里的选型重点不是哪个框架更新，而是“编辑能力”和“渲染性能”哪个更重要。**

例如，编辑几十个多边形，Konva 可能比引入复杂 GPU 渲染方案更直接。

---

## 6. 三维可视化：以空间、模型和场景交互为核心

如果你的软件需要：

- 加载 3D 设备模型。
- 在三维空间中查看设备状态。
- 自由旋转、缩放、漫游。
- 展示三维工厂或数字孪生场景。
- 在模型上标记设备位置和报警状态。

就应该考虑三维图形引擎。

| 技术 | 主要特点 | 适用场景 |
|--------|--------|--------|
| **Three.js** | 灵活的 Web 三维图形库 | 三维展示、数字孪生、可视化 |
| **Babylon.js** | 功能完整的 Web 3D 引擎 | 复杂三维交互、场景和工具 |
| **React Three Fiber** | 在 React 中组织 Three.js 场景 | React 项目中的三维组件化开发 |

官方项目：

[Three.js](https://github.com/mrdoob/three.js) · [Babylon.js](https://github.com/BabylonJS/Babylon.js) · [React Three Fiber](https://github.com/pmndrs/react-three-fiber)

注意，Three.js 和 React Three Fiber 不是两个完全独立的三维引擎。

React Three Fiber 是围绕 Three.js 的 React 渲染层。

## 三、一个更重要的认知：同一个软件可以有多个渲染体系

假设你开发一个功能比较完整的桌面平台。

它同时包含：

- 设备管理。
- 复杂任务配置。
- 实时监控。
- 视频叠加。
- 二维区域编辑。
- 三维设备展示。

那么不需要强迫所有页面使用同一种渲染技术。

### 多种 UI 技术协同的典型架构

**React + Tailwind CSS + shadcn/ui**

统一页面结构、导航、基础组件、视觉规范

**统一设计系统**

颜色、字体、布局、交互、组件规范

但是，要注意一个潜在问题：

**多种渲染技术可以共存，不代表它们应该各自维护独立的交互规则和视觉风格。**

例如，PixiJS 画布中的选中颜色、Konva 编辑器中的控制点样式、Three.js 场景中的报警标记，都应该尽可能遵循同一套产品设计语义。

## 四、按场景判断

<details>
<summary>普通管理后台</summary>

优先使用现有页面框架与共享组件。复杂分组或表格虚拟化出现后再评估 TanStack Table 或 AG Grid。

</details>

<details>
<summary>监控大屏或视频叠加</summary>

先测更新频率、图层数量和同步误差。图表优先评估 ECharts。视频检测框可从 Canvas 2D 开始，在性能目标未达到时试测 PixiJS 或 WebGL。

</details>

<details>
<summary>二维编辑与三维场景</summary>

拖拽多边形可先验证 Konva 或 Fabric.js。空间漫游、三维模型交互和拾取则考虑 Three.js 或 Babylon.js。统一状态颜色和选择、取消的交互规则。

</details>

## 五、以后怎样让 AI 自动完成 UI 技术选型？

你可以直接使用下面的提示词。

### 多场景 UI 技术选型提示词

```text
我正在开发一款软件，包含以下界面需求：【填写页面及功能】。

请先按照普通 UI、复杂表格、统计图表、实时视频叠加、二维交互画布、三维可视化等类型对页面进行分类。

为每一类选择成熟的技术方案，优先复用现有前端框架和组件体系。

比较相关开源技术，说明哪些技术互补、哪些职责重叠。

重点考虑性能、交互复杂度、统一视觉规范、许可证和长期维护成本。

先输出技术选型表和组件复用方案，不要直接开始编写代码。
```

## 六、本课最重要的五个结论

1. **React 不负责解决所有图形绘制问题。** 它可以组织页面，让专业图形引擎负责特定区域。
2. **普通 UI 优先使用成熟组件。** 不要自己开发按钮、表单和弹窗。
3. **复杂表格、二维编辑和三维场景需要专门的技术。** 不同问题有不同工具。
4. **Canvas、PixiJS、WebGL 并非越高级越好。** 先满足需求，再考虑更复杂的渲染方案。
5. **多种技术可以共存，但设计系统必须统一。**
